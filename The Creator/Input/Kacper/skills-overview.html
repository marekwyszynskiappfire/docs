Two skills, one workflow

Cursor skills for Timetracker QA CoE E2E: draft manual tests in Jira/XRay format, then implement approved cases as Playwright specs. Neither skill creates Jira issues automatically.

TestCaseWriting AutomatingTestCases Human imports to Jira

TestCaseWriting

Manual UI test cases — Action, Data, Expected Result. XRay-ready CSV. E2E candidate recommendations.

Output: Markdown tables + CSV blocks for human review and Jira import.

AutomatingTestCases

Playwright implementation under qa-coe/E2E/Timetracker/. Reuses views/, api/, date isolation.

Output: TTQA-N.case.ts + scenario registration.

Context (not step authority): Jira stories and epics you send — AC, scope, parent epic. Helps coverage and Preliminary drafts; approved XRay steps still win for wording.

TestCaseWriting skill

Manual / XRay

When to use

  • New user-facing feature or UI regression
  • Convert exploratory notes → structured cases
  • Recommend E2E automation candidates (2–5 per slice)

Jira story & epic context

When you paste, link, or export Jira stories or epics, the skill uses them for scope and acceptance criteria — feature intent, parent epic, what to cover, and open assumptions.

Not a substitute for approved XRay steps. Story AC alone → Preliminary until code/UI is verified. TT-* / EPIC-* ≠ KAN-* issue under test — still ask for work-item key, summary, and id when Data needs an issue.

Ask before drafting (minimum)

What it produces

Step format: Action | Data | Expected Result (CSV: 3 columns only)

Description block in Jira (preconditions, aliases) — not in CSV

Status labels: Final draft vs Preliminary — assumptions must be listed

Does NOT: auto-create Jira/XRay issues, borrow KAN-* from other TTQA cases

Workflow

Ask user → read Jira story/epic if sent → grep example specs → verify code/UI
→ layer coverage (access → shell → happy path → edges)
→ draft + CSV → human review → Jira import
→ (optional) hand off to AutomatingTestCases

Expected Result// comment + expect* assertions

✓ Good testStep

testStep(
  "Open Weekly module and go to week. week: 5 months ago; TotalTime1: 1h 00m",
  async () => { … }
);

✗ Never

testStep(
  `Date1: ${date1Label}; IssueKey1: ${ISSUE_KEY}`,
  async () => { … }
);

Hard rules (both skills)

Never invent TTQA-* Never borrow KAN-* No ${} in testStep
  • testStep titles: static "..." literals only — no template literals, no ${…}
  • Dates in steps: relative labels (5 months ago) — not today or moment().format() in titles
  • Weekly clock times: test.use({ timezoneId: "UTC" }) + UTC seed via moment.utc(...)
  • Weekly hover: times on card; tooltip = project/summary (usually not times)
  • Scenario ids: TS-5a not bare TS-5
  • Stage: always DEVELOP | REVIEW — do not ask user
